# 秋招信息收集项目调研

> 调研时间：2026-09-22
> 方法：GitHub 搜索（认证 API）+ 逐仓库 clone 审计提交历史与数据文件 + 在线端点实测
> 核心筛选标准：**数据是否真的在更新**，而非只看 README 声称

## 为什么"数据真实性"是第一筛选标准

本次调研的起因是上游项目 `xixicc186/xixicc2027` 存在**假更新**：README 写着「每日更新 ｜ 更新时间：2026-09-22」，但实际审计发现：

- `jobs.json` 最后一次真实改动是 **2026-09-03**（19 天前）
- 自 09-04 起连续 **18 次**「每日自动更新」提交，**每次只改 README 里那一行时间戳**，数据文件一次没动
- 数据内 `last_seen` 字段最新只到 **2026-07-16**，8 月、9 月新增记录均为 **0 条**
- 远端 `raw.githubusercontent.com` 上的 jobs.json 与仓库本地**字节级完全相同**

结论：爬虫早已失效，只有时间戳在自动刷新。因此下面每个项目都做了同等深度的验证。

## 五、结论与建议

**如果要「一份能持续跟进的秋招信息」**，按可用性排序：

1. **ruyi1/campus-radar** — 最稳。83 天连续日报不断档，纯 GitHub Actions 跑，改 `config.py` 指定你的方向和城市即可。
2. **cloud666666666/daily-jobs** — 最适合自己掌控。MIT 协议、零依赖、双数据源，龙哥表无需凭据即可跑。偏 AI/算法岗。
3. **setozjl/campus-jobs-radar-mcp** — 如果你想让我（AI 助手）直接帮你查国央企，这个 MCP 接进来最顺手（查岗位、盯截止日都能自然语言问）。**但需要你用微信扫码拿一个免费 key 给我**，否则只能用 10 次/天且我现在无法验证它的数据新鲜度。

**方法论层面的三条经验**（来自本次审计）：

1. **别信 README 的「每日更新」**。要查 `git log -- <数据文件>` 看数据文件本身最后一次改动时间，而不是看最近一次提交时间。
2. **要查数据内部的时间字段**（如 `last_seen` / `first_seen`），它能揭穿"文件被提交但内容是旧的"。
3. **比对远端与本地字节**（`cmp`），确认线上拿到的就是仓库里的，排除缓存或中间层。

**当前项目（xixicc2027）的处置建议**：数据已确认失效，若继续用需自行接入新数据源，或直接改用上面的 `cloud666666666/daily-jobs`（同为本项目自带的 skill 思路，但数据源是活的）。
