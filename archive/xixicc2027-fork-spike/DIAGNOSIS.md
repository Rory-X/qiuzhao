## 一句话结论

**爬虫约在 2026-07-16 夜里失效，之后 67 天里「发布层」每天照常跑、「采集层」完全空转——
所以仓库看着天天有提交，内容其实一个字节都没变。fork 之后只要把采集端重写，
整条链路能跑通：本目录已用真实抓取验证过，并且原项目的发布端被证明是确定性可复刻的。**

## 一、证据：两条生命线

仓库每天有 `每日自动更新` 提交，但把 68 个提交全回放后，真相是**两条独立的生命线**：

| 日期 | 条数 | 新增 | 删除 | 采集层 | 发布层 |
|---|---|---|---|---|---|
| 07-14 | 444 | **82** | 5 | ✅ 工作 | ✅ 跑了 |
| 07-15 | 456 | **18** | 6 | ✅ 工作 | ✅ 跑了 |
| 07-16 | 466 | **19** | 9 | ✅ 工作 | ✅ 跑了 |
| 07-17 | 478 | **15** | 3 | ✅ 工作 | ✅ 跑了 |
| 07-18 | 475 | 0 | 3 | ❌ **空转** | ✅ 跑了 |
| 07-21 | 467 | 0 | 8 | ❌ 空转 | ✅ 跑了 |
| 08-01 | 451 | 0 | 4 | ❌ 空转 | ✅ 跑了 |
| 08-15 | 447 | 0 | 3 | ❌ 空转 | ✅ 跑了 |
| 09-03 | 443 | 0 | 2 | ❌ 空转 | ✅ 跑了 |
| 09-22 | 443 | 0 | 0 | ❌ 空转 | ✅ 跑了 |

**07-17 之后，「新增」列永远是 0。** 67 天零新增。

### 硬指标

| 指标 | 值 | 含义 |
|---|---|---|
| 最大 `first_seen` | **2026-07-16** | 最后一次成功抓到新条目 |
| 最大 `last_seen` | **2026-07-16** | 最后一次成功「再次看到」已有条目 |
| 07-17 起 `jobs.json` 字节变化 | **0 次**（仅删除过期条目） | 数据只出不进 |
| 条数轨迹 | 478 → 443（**单调递减**） | 只清理旧记录，无新血 |
| 数据池年龄中位数 | **74 天** | 443 条里没有一条是 7 天内见过的 |

现有数据里**最新的一条也已经是 68 天前的信息**。

### 为什么看着像"在更新"

每日提交确实存在，因为**发布层还活着**：

- 提交只改 README 第 3 行的日期（`1 insertion, 1 deletion`）
- `jobs.json` 从 09-03 起哈希恒定 `f85c719766a5`
- 09-22 的 README 说"更新时间：2026-09-22 00:00 ｜ 共 442 条"——
  **日期是真的，条数也是真的，但数据是 7 月的**

## 二、根因：采集端死了，发布端没死

### 发布端被证明是「确定性纯函数」

我用 `publisher.py` 复刻了 README 和 index.html 的生成逻辑，对仓库现有 `jobs.json` 渲染：

```
README.md    字节级一致 ✅（shasum c3d0e3101bc93f40c1165c15599a462a36cf0e81）
index.html   字节级一致 ✅
```

复刻出的两条隐藏规则（原先不可见）：

1. **行业顺序是固定枚举**，不是按数量排序：
   `互联网 · 游戏 · 半导体/硬件 · 新能源车企 · 传统车企 · 外企 · 快消/零售 · 医药/生物 · 银行/金融 · 制造业 · 其他 · 军工/研究所 · 高校/事业单位 · 央国企`
2. **表格里 positions / locations 各只取前 4 项**（`cap=4`）
3. README 共 442 条 = jobs.json 443 条 **减去 `campus_only=true` 的 1 条**

**既然发布端是纯函数，那么它每天"跑成功"完全不需要采集端也活着。**
这就是"静默失效"能持续 67 天没被发现的原因。

### 合并层也被精确复刻

`merge.py` 的去重与清理规则，经 **68/68 天全历史回放验证**：

| 规则 | 内容 | 验证 |
|---|---|---|
| 去重键 | `company + cohort + batch + program`（**不含 positions**） | 68/68 天条数一致 |
| 过期清理 | `deadline < 今天` → 移除 | 58/58 条删除都发生在**截止日 +1 天** |
| 交叉确认 | 同键再现 → `confirmed_by += 1`、`last_seen` 推进 | README 的 `✅×N` 即来于此 |

> 踩坑记录：去重键若含 `positions`，回放会恒定多 4 条。
> 原因：`positions` 会随渠道更新而漂移（汇川技术 6 项 → 4 项），进键会产生重复记录。
> 正确做法是**按公司+届别+批次+项目归并，保留较全的 positions**。

### 那"爬虫为什么失败"？

**爬虫代码根本不在仓库里**，所以只能靠数据形态反推：

| 排查项 | 结果 |
|---|---|
| 全历史文件树 | 只有 `jobs.json` / `README.md` / `index.html` / 模板 / skill，**无任何爬虫源码** |
| Actions workflows | 仓库只有 1 个 `pages-build-deployment`（官方 Pages 构建），**无采集任务** |
| 作者其他仓库 | 14 个公开仓库，`collector-agent` 是「收藏内容沉淀」工具，与秋招无关 |
| 提交者 | 全部是 `xixicc186` 本人，无 bot 身份 |

所以采集端是**跑在作者本地或私有环境的外部脚本**，从未开源。
它的失败**无法从仓库内部定位到具体那行代码**，但失效模式有强特征：

> **07-17 之后连 `last_seen` 都不再推进** —— 说明不是"抓到了但解析失败"，
> 而是**请求/入库整条链路断了**：要么调度没再触发，要么数据源请求被拒，
> 要么抓取结果始终为空集。

注意 07-18 起**过期清理仍然正常工作**（每天还在删到期条目），
说明脚本**还在被调用**，只是"抓新数据"这一步产出了空集。
最可能是**数据源侧被反爬拦住或接口失效**，产出空列表，而代码
"空结果不报错"继续走完了清理+渲染+提交 —— 于是静默失效。

## 三、fork 能不能跑通？能，已实测

### 数据源还活着

原项目靠"公开渠道 + LLM 抽取"，微信生态（`official_wechat` 字段、`weixin.qq.com/r/` 短链）是主来源之一。
实测**搜狗微信搜索仍可正常抓取**：

```
6 连续查询        HTTP 200，均 10 条/页，无验证码拦截
分页            page1~5 各 10 条，可翻页
返回时间戳       2026-09-22 08:10 ~ 15:58（就是今天）
```

### 端到端已经跑通

`pipeline.py` 采集 → 合并 → 渲染全链路实测：

```
① 采集     抓 24 篇 → 结构化 20 条
② 合并     基线 443 + 新抓 20 → 461（新增 18 / 确认刷新 2 / 字段补全 2 / 过期清理 0）
③ 渲染     README.md + index.html ✅
④ 校验     残留过期条目 0 ✅
```

### 但抽取质量是真实门槛

`company` 抽取的准确率（24 例人工标注集）：

| 版本 | 准确率 | 说明 |
|---|---|---|
| v1 朴素正则 | **47%** | `2027届` 被吞进公司名；"秋招速报"误判为公司 |
| v3 分段+后缀 | 79% | 按分隔符切段 |
| **v4 当前实现** | **96%** | 段内去年份 + 优先带企业后缀 + 媒体词黑名单 |

`industry` 分类的准确率**极依赖正文**：

| 输入 | 准确率 |
|---|---|
| 仅标题 | **25%** |
| 标题 + 正文 | **100%** （15/15） |

**结论：必须抓正文。** 只拿搜索结果的标题做分类是不可用的
（"京东方"→其他、"腾讯"→其他、"比亚迪"→其他 都会错）。

### 字段可达性（实测）

| 字段 | 可达性 | 备注 |
|---|---|---|
| `company` | ✅ 96% | 需 v4 级抽取器 |
| `cohort` / `batch` / `industry` | ✅ 100%（带正文） | |
| `positions` / `locations` | ⚠️ 40~80% | 正则易串味，建议上 LLM |
| `apply_url` | ⚠️ ~10% | 正文外链；`qr61.cn` 等短链多 |
| `deadline` | ⚠️ 低 | 常以图片或"招满即止"表述，正则难 |
| `official_wechat` | ❌ | 见下 |
| `qr_image` | ❌ | 全库 443 条**均为 null**，原项目也没填上 |

> 关于 `official_wechat`：443 条里 106 条有值，但**只对应 37 个不同链接**，
> 其中一个被 **56 条不同公司共用**。这不是各公司官方公众号，
> 而是采集时统一填的「引导关注」短链，属占位值。
> fork 时这个字段可以直接放弃或用 LLM 从正文重抽。

## 四、fork 实施建议

### 结论：**能跑通，且成本可控**

原项目的**发布端和合并端已被证明是确定性逻辑**，不用重写。
需要新建的只有**采集端**，而数据源仍可访问。

### 落地路径

1. **保留** `site_template_heytea.html`（前端零改动）
2. **复用** `publisher.py`（README/index.html 渲染，已字节级验证）
3. **复用** `merge.py`（去重 + 确认 + 过期清理，已 68/68 回放验证）
4. **重写** `collector`（本目录 `collector_spike.py` 可直接当起点）
5. **起底数据**：把原库 443 条作为 history 基线并入，`confirmed_by` 继续累积

### 必须解决的三个问题

| 问题 | 建议 |
|---|---|
| `positions`/`locations`/`deadline` 抽取不稳 | 接 LLM 抽取（原项目 README 明说用了 LLM），正则只做兜底 |
| 单源脆弱（搜狗一挂就全挂） | 多源冗余：微信 + 牛客 + 各公司招聘站 sitemap |
| **静默失效**（本次事故根因） | 加**健康告警**：若连续 N 天"新增=0"则报错退出（**别静默提交**）。
原项目 67 天空转没人发现，就是因为空结果不报错 |

### 建议加的护栏

```python
# 采集中加入断言：抓到 0 条新记录时，让任务失败而不是照常提交
if stats["new"] == 0:
    sys.exit("!! 今日零新增，疑似采集端失效 —— 请检查数据源")
```
