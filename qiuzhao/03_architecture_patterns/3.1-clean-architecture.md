# 3.1 Clean Architecture

> 能用依赖方向和构造函数注入隔离业务规则，同时识别不值得分层的场景。

## 前置知识

先读 [2.3 API 服务解剖](../02_project_structure/2.3-api-service-anatomy.md)。

## 正文

### 原则先于层名

Clean Architecture 的核心只有一条：源码依赖指向更稳定的业务核心。常见四圈是 entity、use case、interface adapter、framework/driver，但 Go 项目不必建立四个同名目录。重要的是业务规则不 import HTTP、SQL driver 或云厂商 SDK。

```text
framework -> adapter -> use case -> entity
 HTTP          DTO       orchestration  rules
 DB impl       mapping   ports          values
```

### Go 中的依赖反转

use case 在自己这一侧定义需要的最小接口，infra 用具体类型实现；main 同时认识两边并完成组装。

```go
package order

import (
	"context"
	"errors"
)

var ErrOrderIDRequired = errors.New("order id is required")

type Order struct{ ID string }

func NewOrder(id string) (Order, error) {
	if id == "" { return Order{}, ErrOrderIDRequired }
	return Order{ID: id}, nil
}

type OrderStore interface {
	Save(ctx context.Context, order Order) error
}

type PlaceOrder struct{ store OrderStore }

func NewPlaceOrder(store OrderStore) PlaceOrder { return PlaceOrder{store: store} }

func (uc PlaceOrder) Execute(ctx context.Context, id string) error {
	order, err := NewOrder(id)
	if err != nil { return err }
	return uc.store.Save(ctx, order)
}
```

测试只需一个 fake：

```go
package order

import (
	"context"
	"testing"
)

type memoryStore struct{ saved []Order }
func (s *memoryStore) Save(_ context.Context, o Order) error {
	s.saved = append(s.saved, o); return nil
}

func TestPlaceOrderSavesValidOrder(t *testing.T) {
	store := &memoryStore{}
	uc := NewPlaceOrder(store)
	if err := uc.Execute(context.Background(), "order-1"); err != nil {
		t.Fatalf("place order: %v", err)
	}
	if len(store.saved) != 1 || store.saved[0].ID != "order-1" {
		t.Fatalf("saved=%+v, want order-1", store.saved)
	}
}
```

接口不是为了“每个 struct 都可替换”，而是在不稳定 I/O 与需要独立测试的决策之间建立 seam。构造函数使必需依赖显式，Option 模式只应用于真正可选的配置。

### 边界数据转换

HTTP request DTO 在 adapter 解码并转换为用例命令；use case 返回领域结果；adapter 再转换为 response DTO。数据库 record 也不应渗入核心。若三者目前字段完全一致且没有独立演进需求，可暂时共用类型，避免机械映射。

### 何时过度设计

小型 CRUD、单一存储、生命周期很短的工具，通常用 `handler -> service -> repository` 已足够。警示信号包括：每个 use case 只有一行转发；接口只有一个实现、测试也不替换；同一对象在五层间无变化复制；开发者追一次请求需要打开十几个文件。

开始抽象的真实信号是：核心规则复杂、存在多个 transport/driver、外部依赖变化快、需要独立测试决策或团队边界明确。

### 前端人容易踩的坑

- 一比一复制 NestJS module/provider/controller/decorator。
- 在实现方定义大 Repository 接口，让所有消费者被迫依赖全部方法。
- “为了 mock”给每个类型建接口，而不是围绕业务 seam。
- entity 内 import ORM 标签/HTTP 类型，导致依赖反向。
- 把纯 CRUD 包装成几十个空洞 use case。

## 对比前端

NestJS 通过容器和 decorator 绑定 token/provider；Go 常在 `main` 中直接 `NewX(NewY(...))`。Nest 的 class interface 在运行时会消失，Go interface 则参与编译期方法集检查。两者都能做依赖反转，但 Go 更鼓励调用方小接口和显式对象图。

## 检验标准

1. “依赖向内”具体约束的是源码 import 还是运行时调用？
2. 为什么接口通常应由 use case/调用方定义？
3. main 为什么可以同时依赖核心和 infra？
4. 哪些信号说明 Clean Architecture 已过度？
