# 3.5 并发模式

> 能组合 worker pool、fan-out/fan-in、背压、限流和优雅退出，形成受控的并发系统。

## 前置知识

先掌握 [1.3 并发基础](../01_language_basics/1.3-concurrency.md)。

## 正文

### Worker Pool 与背压

固定数量 worker 从有界 jobs channel 取任务，限制并行度和排队内存。提交策略必须显式选择：阻塞等待、立即拒绝、带超时等待或丢弃低优先级任务。

```go
func worker(ctx context.Context, jobs <-chan Job, out chan<- Result) {
	for {
		select {
		case <-ctx.Done(): return
		case job, ok := <-jobs:
			if !ok { return }
			out <- handle(ctx, job)
		}
	}
}
```

队列容量 × 单任务内存决定基础内存风险；worker 数 × 下游成本决定外部压力。两者需用指标和负载测试设定。

### Fan-out / Fan-in 与错误

fan-out 将独立任务并行处理，fan-in 汇聚结果。必须保留输入身份、决定是否保持顺序，并确保错误/取消发生时所有发送者都能退出。标准库适合简单场景；`errgroup.WithContext` 适合“任一失败取消兄弟并收集首个错误”。并发上限可用 semaphore 或固定 worker。

### Rate Limiting

令牌桶允许按速率补充令牌并容忍有限 burst；漏桶/恒速出队让流量更平滑。网关通常需要 tenant、model、provider 多维额度。限流只决定“现在是否允许”，有界队列决定“是否等待”；两者不要混成一个模糊开关。

### 多阶段 Pipeline

`input -> validate -> enrich -> execute -> export` 可用同步函数保持简单。只有 stage 速度差、需要独立扩缩或隔离故障时才在中间放 channel；此时每条边都要定义容量、关闭权、重试和排序。

### 优雅退出

```text
signal received
 -> cancel root context
 -> HTTP server stops accepting new work
 -> workers stop intake and drain/abort by policy
 -> wait for in-flight
 -> shutdown deadline expires: return error / force process exit
```

关闭顺序通常与启动顺序相反。不要在收到信号后立刻 `os.Exit`，它不会运行 defer。HTTP 使用 `Server.Shutdown(ctx)`；后台组件应有 `Run(ctx) error` 或清晰 `Start/Stop` 协议。

### 前端人容易踩的坑

- 用 goroutine 数量代替并发策略，流量一大就无界增长。
- 关闭 jobs 后还有多个 producer 发送。
- fan-in 只读到首个错误就返回，发送方永久阻塞。
- 把 rate limit、concurrency limit、queue capacity 当成同一个参数。
- shutdown 只停 HTTP，不停 worker、ticker、订阅和 exporter。

## 对比前端

Node 常用 p-limit、BullMQ 或自建 async queue 控制并发；Go 的 goroutine 很便宜但资源调用不便宜，因此仍需 worker/令牌/队列。channel 把等待与容量写进进程内代码，却不提供持久化队列语义。AbortController 对应 root context，但 Go 的每个阻塞点都要主动观察取消。
