# 3.3 Go 中的 DDD

> 能用朴素 struct、方法和接口表达领域规则，而不把 Java/TypeScript class 模板搬进 Go。

## 前置知识

理解值/指针接收者与 [3.1 Clean Architecture](3.1-clean-architecture.md)。

## 正文

### 从语言开始，而不是从目录开始

DDD 首先是统一术语、业务边界和不变量。Go 社区通常用少量 struct + 方法表达，而不是 entity/base class/decorator。若团队说“RoutePlan”“Provider”“Session Event”，代码也应使用同样词汇。

### 聚合根和值对象

聚合根负责保护一次事务内必须一致的不变量；外部不应绕过其方法随意改字段。

```go
type Order struct {
	id string
	status Status
	lines []Line
}

func (o *Order) Confirm() error {
	if len(o.lines) == 0 { return ErrEmptyOrder }
	if o.status != Draft { return ErrInvalidTransition }
	o.status = Confirmed
	return nil
}
```

值对象用无导出字段 + 构造函数验证，方法返回新值来表达不可变语义。小 struct 的值复制非常适合 Money、TenantID、Route 等概念。

### 仓储、服务与事件

仓储接口使用领域术语并在领域/use case 侧定义，如 `Order(ctx, id)`、`Save(ctx, order)`，不要暴露 SQL row 或通用 `Find(map[string]any)`。

领域服务放“属于领域但不自然属于单个实体”的纯规则；应用服务负责授权、事务、调用仓储、发布事件和跨聚合编排。两者不要都变成无规则的转发层。

领域事件是已经发生的事实：

```go
type OrderConfirmed struct {
	OrderID string
	At time.Time
}
```

事件可先由方法返回或收集，再由应用层写 outbox。直接从实体向 channel 发送会把领域规则耦合到并发、阻塞和交付策略。

### 何时不用 DDD

纯 CRUD、规则少、领域术语不稳定或团队只有一个简单服务时，用清晰 handler/service/repository 即可。不要为了“聚合根”把数据库行藏进复杂 API，也不要为了“领域事件”给本地函数调用引入消息系统。

### 前端人容易踩的坑

- 用 class 私有字段/继承的样子模拟 DDD，却没有真正业务不变量。
- 每个 noun 都建 entity、repository、factory、service。
- 让 ORM struct 成为所有层的共享领域模型。
- 在实体方法中做网络 I/O，导致规则不可预测、不可单测。
- 事件用现在时命名成命令；事件应是过去式事实。

## 对比前端

TS 常用 class、private 和 decorator；Go 用包级封装、未导出字段、构造函数与方法。Go struct 没有继承，组合使边界更显式。前端 Redux action 也有“事实驱动状态变化”的影子，但后端领域事件还涉及持久化、一致性和跨进程投递。
