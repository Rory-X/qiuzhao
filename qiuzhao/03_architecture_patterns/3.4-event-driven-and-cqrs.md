# 3.4 事件驱动与 CQRS

> 能判断事件溯源、CQRS、Outbox 和消息总线各自解决什么问题以及付出的代价。

## 前置知识

先读 [3.3 Go 中的 DDD](3.3-ddd-in-go.md) 和 [1.3 并发基础](../01_language_basics/1.3-concurrency.md)。

## 正文

### 事件溯源：事件是事实源

普通 CRUD 存当前状态；事件溯源按顺序存不可变事件，通过 replay 折叠出状态。

```go
type EventStore interface {
	Append(ctx context.Context, stream string, expectedVersion int, events ...Event) error
	Load(ctx context.Context, stream string) ([]Event, error)
}

func Replay(events []Event) State {
	var s State
	for _, e := range events { s = Apply(s, e) }
	return s
}
```

`expectedVersion` 用乐观并发防止两个 writer 覆盖同一流。事件 schema 一旦持久化就成为长期契约，需要版本、upcaster、快照与幂等处理。它换来审计、时间旅行和重建读模型，也带来存储增长与演进复杂度。

### CQRS

CQRS 将改变状态的 command 与读取视图的 query 分开。动机是两侧模型、扩展和一致性需求不同，而不是“每个服务都该有两套代码”。读模型异步更新会产生最终一致窗口，UI/调用方必须知道刚写入的数据何时可见。

轻量 CQRS 可以只是不同方法/类型；只有吞吐、存储模型或团队所有权确实不同才拆进程和数据库。

### Outbox 保证提交边界

“写数据库成功后发 Kafka”在两步之间崩溃会丢事件。Outbox 在同一数据库事务中写业务状态和待发布记录，由 worker 重试发送；消费者以 event ID 幂等去重。

```text
transaction: update aggregate + insert outbox row
commit
worker: claim row -> publish -> mark delivered
```

这是 at-least-once，不是魔法 exactly-once；发布成功但标记前崩溃会重复。

### 总线选型与 Saga

- 内存 bus：单进程通知，重启丢失，不适合可靠集成事件。
- NATS：低延迟 pub/sub；JetStream 提供持久化和消费语义。
- Kafka：高吞吐持久日志、分区顺序和 replay，运维/模型更重。
- Watermill：在 Go 中统一消息 handler/middleware，并不消除底层 broker 语义。

Saga 用一组本地事务和补偿动作完成跨服务流程。补偿不是数据库回滚，必须能重试、幂等，并考虑人工介入。Temporal 用持久事件历史与重放表达 durable workflow，是更完整的执行模型。

### 前端人容易踩的坑

- 把 Redux action 类比成可靠消息，忽略持久化、重复、乱序和 schema 演进。
- 同时上 event sourcing、CQRS、Kafka，只因它们经常一起出现。
- 认为 broker 的 “exactly once” 消除了业务幂等。
- 修改旧事件内容，导致历史重放结果变化。
- outbox worker 没有 claim/lease，多个实例重复抢任务且无观测。

## 对比前端

Redux 的 `(state, action) -> state` 很像 replay 的 reducer，这个映射有助于理解确定性；区别是后端事件是长期业务记录，需要版本兼容、并发控制和投递协议。CQRS read model 类似为 UI 预计算 selector 结果，但它可能跨进程并延迟更新。
