## 正文

### 栈、堆与逃逸分析

Go 编译器根据值是否逃出当前调用决定放栈还是堆，不由 `new` 或 `&` 直接决定。返回局部变量地址是安全的；若它逃逸，编译器会放到堆上。用 `go build -gcflags='-m=2' ./...` 观察逃逸原因，但不要为了“零分配”牺牲清晰度。

### slice：三个字段的视图

slice 可理解为指向底层数组的指针、长度 `len` 和容量 `cap`。复制 slice 只复制这三个字段，元素仍共享。

```go
package main

import "fmt"

func main() {
	a := []int{1, 2, 3, 4}
	b := a[:2]
	b[0] = 9            // a[0] 也变为 9
	b = append(b, 8)    // 容量足够，写入 a 的底层数组
	c := append([]int(nil), a...) // 显式独立副本
	fmt.Println(a, b, c)
}
```

append 可能原地扩展，也可能分配新数组，因此不要依赖调用前后的 slice 一定共享或一定不共享。保留一个很小的 subslice 也可能让巨大底层数组无法回收。

### map、string 和分配

map 是哈希结构，扩容细节属于 runtime 实现，不应成为业务依赖。迭代顺序不稳定；并发写或读写不安全，需用锁、单 owner goroutine 或其他明确策略。读取不存在的 key 得到零值，因此用 `v, ok := m[k]` 区分“不存在”。

string 是不可变字节序列，不保证内容是合法 UTF-8。`len(s)` 返回字节数；`for range` 按 rune 解码。`[]byte(s)` 与 `string(b)` 通常会复制，热路径需通过 benchmark 验证影响。

### GC 和 GMP 调度

Go 的并发、增量式三色标记 GC 通过 write barrier 维护标记正确性；仍存在短暂 STW 阶段，但应用更常见的问题是分配率和活跃堆太大，而不是“GC 算法不够先进”。`GOGC` 控制相对堆增长目标，`GOMEMLIMIT` 给 runtime 软内存上限；改参数前先测。

GMP 模型：G 是 goroutine，M 是 OS thread，P 是执行 Go 代码所需的调度资源。阻塞系统调用不等于阻塞所有 goroutine。与 V8 事件循环不同，Go 代码可能真正并行，因而共享内存必须同步。

### 观察工具

```bash
go test -bench=. -benchmem ./...
go test -run '^$' -bench BenchmarkX -cpuprofile cpu.out
go tool pprof cpu.out
go test -trace trace.out ./path/to/package
go tool trace trace.out
GODEBUG=gctrace=1 go test ./...
```

CPU profile 回答时间花在哪，heap profile 回答哪些分配仍存活，allocs profile 回答谁制造分配，trace 用于观察调度、阻塞、GC 和 goroutine 生命周期。一次只改变一个因素，并保存基准前后结果。

### 前端人容易踩的坑

- 把 slice 当成独立数组，忽略共享底层存储。
- 依赖 map 顺序生成稳定输出或签名。
- 用 `len(string)` 计算字符数。
- 看到 `&local` 就认定“危险”或“必在堆上”。
- 凭直觉调 `GOGC`，没有 profile、负载模型和延迟分位数。

## 对比前端

V8 也有分代 GC 和优化编译，但 JS 对象普遍具有引用身份；Go 给你更多值语义和连续数据布局。Node 事件循环把许多 I/O 回调串在一个 JS 线程上，Go runtime 则在多个 M/P 上调度 G。两边都应先 profile，不能靠语言刻板印象判断瓶颈。
