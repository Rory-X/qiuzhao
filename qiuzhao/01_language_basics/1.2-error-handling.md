# 1.2 错误处理

> 能设计可判断、可追踪、不会泄漏实现细节的 Go 错误链。

## 前置知识

先读 [1.1 类型与接口](1.1-types-and-interfaces.md)，理解接口值和类型断言。

## TypeScript 迁移地图

| 熟悉的 TS 概念 | 本篇先建立的 Go 映射 |
|---|---|
| `throw` / rejected Promise | 显式 `(T, error)` 返回值 |
| `Error` subclass | sentinel、自定义错误类型与行为接口 |
| `cause` / `instanceof` | `%w`、`errors.Is`、`errors.As` |
| 全局 error middleware | 边界集中记录与协议状态映射 |

## 正文

### error 是返回值，不是控制流机关

Go 没有日常业务用的 `try/catch`。函数把失败作为最后一个返回值，调用者立即处理：

```go
package main

import (
	"fmt"
	"os"
)

func read(path string) ([]byte, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("read config %q: %w", path, err)
	}
	return data, nil
}

func main() {
	_, err := read("missing.json")
	fmt.Println(err != nil)
}
```

这与 Promise rejection 最大的不同是：错误属于函数签名，沿普通分支传播；编译器不会强制检查，但代码审查能在调用点直接看到处理策略。

### 分类：sentinel、类型和行为

稳定且无需附加字段的分类可用 sentinel：

```go
var ErrNotFound = errors.New("not found")
```

需要携带结构化上下文时用自定义类型：

```go
type ValidationError struct {
	Field string
	Reason string
}

func (e *ValidationError) Error() string {
	return e.Field + ": " + e.Reason
}
```

调用方用 `errors.Is(err, ErrNotFound)` 穿透 `%w` 包装判断等价错误；用 `errors.As(err, &target)` 查找错误链中的具体类型。跨模块时，行为接口（如 `Temporary() bool`）能避免依赖具体实现，但只应在确有稳定行为语义时使用。

### 包装和分层传播

每层只增加对定位有用的上下文，并用 `%w` 保留原因：

```text
HTTP: 映射公开错误类别到状态码，不返回内部详情
use case: 加动作上下文，如 "create resource"
repository/provider: 加目标信息，如 "query resource 42"
driver: 返回原始数据库或网络错误
```

不要每层都记录同一个错误；通常在系统边界记录一次，并带完整链、request ID 和结构化属性。业务核心返回稳定错误类别，HTTP 层集中映射 400/404/409/429/503。

```go
func statusFor(err error) int {
	switch {
	case errors.Is(err, ErrNotFound): return http.StatusNotFound
	case errors.Is(err, context.DeadlineExceeded): return http.StatusGatewayTimeout
	default: return http.StatusInternalServerError
	}
}
```

### panic/recover 的边界

`panic` 用于进程无法合理继续的不变量破坏或程序员错误，例如启动时必需配置无效。普通输入错误、网络失败和数据库失败都应返回 `error`。`recover` 只能在 goroutine 顶层或 HTTP 边界阻止单次故障拖垮进程；恢复后仍要记录堆栈并返回失败，不能假装成功。

### 前端人容易踩的坑

- 写 `if err != nil { return err }` 丢掉“正在做什么”的上下文。
- 用字符串比较错误；包装后立刻失效，应使用 `errors.Is/As`。
- 既包装又用 `%v`，导致原始错误无法被 `Is/As` 找到。
- 为模拟异常而 panic，照搬 `throw` 心智模型。
- 在每层重复 log，产生同一故障的日志风暴。
- 将 SQL、provider 响应或密钥信息直接返回客户端。

## 对比前端

TS 的 `throw` 会跳过中间语句，错误类型通常不在签名里；Go 的 `(T, error)` 让成功值与失败在每个调用点显式分叉。`errors.Is` 类似检查 cause 链，`errors.As` 类似安全的 `instanceof`，而 `%w` 对应保留 `cause` 同时增加上下文。
