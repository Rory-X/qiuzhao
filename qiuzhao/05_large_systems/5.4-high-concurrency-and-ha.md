# 5.4 高并发与高可用

> 能用背压、熔断、优雅关停、幂等和 Outbox 把故障限制在可控边界内。

## 前置知识

先读 [3.5 并发模式](../03_architecture_patterns/3.5-concurrency-patterns.md) 与 [5.3 可观测性](5.3-observability-and-telemetry.md)。

## 正文

### 背压：拒绝比排队到崩溃更可靠

Capstone 有两个不同控制点：`provider.Queue` 用有界 channel 限制等待任务，满时返回 `ErrQueueFull`；`BoundedClient` 用令牌 channel 限制 in-flight provider 调用，满时快速返回 classified error。前者控制排队内存，后者控制并行下游压力。

生产策略需按端点声明：block（吞吐平滑但占连接）、timeout wait、reject 429/503、drop best-effort telemetry。必须暴露 depth、wait time、reject/drop 指标，容量来自负载测试而非随手常量。

### 熔断状态机

`TimedBreaker` 表达 Closed → Open → HalfOpen：连续可重试失败达到阈值后 Open；cooldown 到期允许试探；成功回 Closed，失败重开。注入 `now func() time.Time` 让测试无需 sleep。

```text
Closed --threshold failures--> Open
Open --cooldown--> HalfOpen
HalfOpen --success--> Closed
HalfOpen --retryable failure--> Open
```

breaker 应按 provider/endpoint 选择粒度；客户端 4xx 不计入下游健康。与 retry、fallback 配合时要有全局 attempt/deadline budget，并加 jitter，防止半开时实例群同时探测。

### 生命周期与优雅关停

`lifecycle.App` 并行 Start 组件；root context 正常取消后，用独立 timeout context 逆序 Shutdown。将 HTTP ingress 放在组件列表靠后，可使逆序关闭时先停止入口，再 drain worker/exporter。注意当前学习实现收到组件 `Start` 错误时会直接返回，尚未进入同一清理路径；生产化必须先 cancel 兄弟组件并执行逆序 Shutdown，再返回启动错误。

生产关停检查：readiness 先转失败；`Server.Shutdown` 停新连接并等待 handler；停止 queue intake；处理/转移 in-flight；flush outbox/telemetry；释放 lease/连接；deadline 到后记录未完成量并退出。不要让所有组件共享已经取消的 context 做清理。

### 幂等

`idempotency.Store.Claim(ctx, key)` 原子判断并占用 key，重复返回 false。真实实现需持久共享存储、TTL、tenant scope，并保存首次响应/最终状态；否则请求第一次占位后崩溃会永久卡住或错误重复执行。

幂等 key 应绑定规范化操作主体，不能让不同 payload 复用同 key。工具调用、支付/发信等外部副作用要把 session/tool-call ID 传到下游作为幂等依据。

### Outbox 最终一致

`outbox.Worker.RunOnce` claim 到期事件，发布成功 MarkDone；失败按 backoff 设置下次可用时间，超出 MaxAttempts 进入 dead letter。注入 clock/backoff 让行为可测。

当前 MemoryStore 的 `ClaimDue` 没有 lease/claimed 状态，多 worker 会并发取同一事件；这在学习版靠消费者幂等承受，生产数据库应使用行锁/lease/skip locked 等 claim 协议，并处理 worker 崩溃后 lease 过期。发布成功但 MarkDone 失败仍会重复，因此消费者必须幂等。

### 高可用不是多开几个副本

无状态 HTTP 可多实例，但 quota、breaker、idempotency、event/outbox state 的一致范围必须明确。可选择本地快速保护 + 共享全局额度；分区/leader ownership；外部持久 store。HA 还需要 readiness、跨 zone、滚动发布、配置版本、数据备份/恢复演练和容量余量。

### 前端人容易踩的坑

- 无限 goroutine/队列，以为 runtime 会自动背压。
- 每个实例本地 token limiter，却宣称是全局 tenant quota。
- retry、fallback、broker redelivery 三层相乘。
- shutdown 取消所有 context 后才尝试 flush。
- 把幂等理解为“查一下是否存在”，缺少原子 claim 和 payload 绑定。

## 对比前端

前端 debounce/throttle 控制单客户端事件，服务端限流/背压控制所有实例与下游资源。AbortController 可取消一次请求，但进程关停还涉及 listener、worker、queue、lease 和 exporter 的顺序。localStorage 去重不等同跨实例原子幂等。
