# 5.5 生产就绪

> 能用一份可执行 checklist 将学习实现审查为可发布、可观测、可恢复的服务。

## 前置知识

完成 05 章前四篇，并能运行 capstone 全部测试。

## 正文

### 配置

推荐优先级 `flag > env > file > default`，但团队必须固定并记录。配置先解析为 typed struct，再一次性 Validate；secret 只存引用/环境注入，不打印。动态配置使用 versioned immutable snapshot，记录 actor、diff summary、时间与 rollback。

- [ ] 每个配置项有默认值、范围、敏感级别和 reload 语义。
- [ ] 未知字段/无效 provider-policy 组合在启动或 swap 前失败。
- [ ] 生产不使用 `example.com` module identity/演示凭据。
- [ ] secret 可轮换，日志和错误不会泄漏。

### 健康与生命周期

Liveness 只回答进程是否卡死，失败会触发重启；readiness 回答当前是否应接流量，依赖初始化、draining 和关键资源状态。不要因一个可 fallback provider 失败就杀进程。

- [ ] `/livez` 与 `/readyz` 语义分离，检查有 timeout。
- [ ] SIGTERM 先让 readiness 失败，再停止 ingress。
- [ ] HTTP 有 read-header/read/write/idle timeout 和 body size limit。
- [ ] worker、ticker、subscription、exporter 都有 owner 与 shutdown。
- [ ] shutdown deadline 与平台 termination grace period 匹配。

### 部署与容灾

容器镜像使用固定 Go/toolchain 与依赖、非 root 用户、最小运行层和 SBOM/漏洞扫描。滚动更新要求版本兼容：新旧实例并存时 API、事件、数据库 schema 和配置都能工作。蓝绿降低切流风险但增加双环境成本。

- [ ] 至少跨故障域多实例，设置 requests/limits 和 PodDisruptionBudget 类约束。
- [ ] 数据有加密备份、RPO/RTO，且做过恢复演练。
- [ ] 数据库迁移 expand → deploy → contract，可回滚应用。
- [ ] provider/region 故障有降级、限额和手动 kill switch。
- [ ] 配置 rollback 与应用 rollback 独立可操作。

### SLO、指标与告警

先定义用户可见 SLI：成功率、首 token/完整响应延迟、Agent 完成率；再定 SLO 与 error budget。告警面向症状和预算消耗，而不是所有单点指标。

- [ ] 记录 rate/error/duration，并监控 p95/p99。
- [ ] provider queue/reject/in-flight、breaker、fallback、token/cost 可见。
- [ ] event append conflict、tool failure、step-budget exceed、outbox dead letter 可见。
- [ ] telemetry 自身 drop/export failure 可见。
- [ ] 每个告警链接 dashboard 和 runbook，并定期演练。

### 安全

- [ ] 外部和内部流量使用 TLS；认证与 tenant 授权分离。
- [ ] 输入做 JSON schema/字段/长度/URL/模型白名单验证。
- [ ] 工具按 principal/tenant 做 allowlist，网络与文件能力沙箱化。
- [ ] prompt、response、RAG 文档、token、PII 有分类、脱敏和保留期。
- [ ] 审计日志防篡改并受访问控制；日志无 API key/Authorization。
- [ ] 依赖、镜像和生成物有来源验证与升级流程。

### 可靠性与数据语义

- [ ] 所有重试有次数、deadline、指数 backoff + jitter；不可重试错误明确。
- [ ] queue 有界且满载行为写进 API/Runbook。
- [ ] idempotency key 跨实例持久、带 TTL/状态/响应和 payload 校验。
- [ ] Event Store append 使用 expected version；schema 有 upcaster/兼容测试。
- [ ] Outbox claim 有 lease，消费者幂等，dead letter 可重放。
- [ ] SSE 从 cursor 重连，明确事件保留和慢消费者策略。

### 性能调优流程

1. 复现代表性负载，固定数据、并发、provider 延迟和 SLO。
2. 同时记录 CPU、heap/allocs、goroutine、mutex/block profile 与 trace。
3. 找最大约束：CPU、GC、锁、queue、网络还是下游。
4. 做一个最小修改，运行 benchmark + 端到端负载并比较分位数/资源。
5. 保留回归测试和 dashboard；收益不足则撤销复杂化。

```bash
go test -race ./...
go test -bench=. -benchmem ./...
go test -run '^$' -bench BenchmarkX -cpuprofile cpu.out
go tool pprof cpu.out
go test -trace trace.out ./...
```

不要把 microbenchmark 的 ns/op 直接当生产吞吐，也不要在没有 profile 时引入对象池。AI 系统常由 provider latency/cost 主导，先优化并发保护、流式首包和缓存命中。

### Capstone 差距清单

Capstone 已用测试证明核心机制，但它明确是学习版：内存 store/limiter/audit/telemetry、fake provider、最小 HTTP 启动、不完整 exporter close/flush、无认证/TLS/真实 SSE/持久数据库/分布式协调。生产化应逐项替换 adapter，同时保持 core/runner 行为测试稳定，而不是直接部署 demo。

### 前端人容易踩的坑

- “本地 go test 全绿”就等于生产就绪。
- 只做 liveness，滚动更新期间仍向 draining 实例发新请求。
- 先调 GC/对象池，忽略 provider timeout 与队列设计。
- 将所有错误告警，值班被噪音淹没。
- 在日志平台无限保留 prompt/response，造成安全与成本风险。

## 对比前端

前端发布关注 bundle、浏览器兼容、RUM 和回滚；后端还要承担长连接、在途请求、持久状态、迁移、跨实例协调和 on-call。两者共同原则是渐进发布、用户可见 SLI、可回滚与真实环境观测。

## 检验标准

1. liveness 与 readiness 的失败后果为何不同？
2. 滚动发布时哪些契约必须支持新旧版本共存？
3. SLO 与普通指标阈值告警有什么区别？
4. 性能调优的证据闭环是什么？
5. 为什么 capstone 当前不能直接作为生产服务部署？
