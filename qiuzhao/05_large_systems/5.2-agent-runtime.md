# 5.2 Agent Runtime

> 能用事件历史、Runner、工具注册表和图状态机管理可恢复的 Agent 会话。

## 前置知识

先读 [3.4 事件驱动与 CQRS](../03_architecture_patterns/3.4-event-driven-and-cqrs.md) 和 [5.1 AI Gateway](5.1-ai-gateway.md)。

## 正文

### Runtime 管理什么

模型只产生下一步建议；Runtime 负责把它变成受控执行：

- 会话：session ID、状态、deadline、并发 run 与恢复策略。
- 事件：用户消息、工具开始/完成/失败、节点迁移、中断和完成。
- 工具：注册、参数/权限验证、调用、timeout、重试和结果限制。
- 编排：step budget、状态机/DAG、human-in-the-loop。
- 重放：从版本化历史确定性恢复可见状态。

### Runner 链路

`Runner.Run(ctx, sessionID, input)` 先追加 `UserMessage`。每一步重新读取事件并 Replay 成 State，交给 Model.Next 产生 `CallTool` 或 `Answer` 命令。

```text
append UserMessage
loop up to 8 steps:
  Load history -> Replay -> Model.Next
  CallTool: append ToolStarted -> Registry.Invoke
            -> append ToolFinished or ToolFailed
  Answer: append AssistantMessage -> append RunCompleted -> return
budget exhausted -> ErrStepBudgetExceeded
```

工具调用先落 `ToolStarted`，结果再落完成/失败，这使历史能解释进程在哪一步停止。当前 MemoryStore 适合测试；生产需要原子 expected-version append、持久化和并发 run 排他/协调。

### 事件版本与重放

`event.Replay` 是纯 reducer，将历史折叠为 messages、running tools 与 status。`StoredEvent` 带版本，upcaster 在 decode/replay 时把旧 payload 升级到当前形状。不要原地改历史事件；新代码必须能读旧版本。

快照可减少长历史 replay 成本，但必须记录快照对应的 stream version，并保留之后事件。重放逻辑不能调用网络、随机数或当前时间。

### 图编排与中断

Graph 按 node ID 查找 `Node.Run(state)`，结果可以 next、complete 或 interrupt。每次迁移落 `NodeTransitioned`；human interrupt 落 `RunInterrupted`；`MaxSteps` 阻止错误图无限循环。当前实现是顺序状态机，不是并行 DAG scheduler；生产还需节点幂等、resume cursor、lease 和补偿。

### 实时流不是事实源

stream.Bus 为订阅者提供有界 channel，慢消费者满时 drop 并计数；`ReplayFrom` 可从事件 Store 和 cursor 补回缺失。正确关系是：持久 history 为 source of truth，SSE/WebSocket bus 只是低延迟投影。

### 与 trpc-agent-go 的对比视角

阅读 [trpc-agent-go](https://github.com/trpc-group/trpc-agent-go) 时关注 agent/model/tool/session/runner 等抽象如何支持多模型、多工具与编排。本 capstone 刻意更小：命令只有 call-tool/answer，Store/Replay 和 graph 直接可见，便于理解 durability seam；成熟框架通常提供更多 callback、middleware、model adapter 与工作流能力，也增加框架约束。选型前先验证事件所有权、恢复语义和工具权限是否符合你的产品。

### 前端人容易踩的坑

- 把内存消息数组当会话事实源，进程重启后无法恢复。
- 工具调用后才记录事件，崩溃时不知道是否已产生外部副作用。
- 允许模型无限循环，没有 step/token/time budget。
- 把 SSE bus 当可靠队列；慢客户端就丢历史。
- replay 时读取 `time.Now()` 或调用 API，导致相同历史得到不同状态。

## 对比前端

Runner 类似 Redux reducer + effect runner：事件/reducer 重建状态，command 驱动外部 effect，再把结果写回事件。但后端 effect 可能扣款、发消息或写数据库，需要幂等 key、超时与崩溃恢复；不能只依赖 UI 状态机。
