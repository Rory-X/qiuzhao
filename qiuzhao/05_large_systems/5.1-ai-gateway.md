# 5.1 AI Gateway

> 能设计多模型 Provider 的统一入口，并沿 capstone 追踪授权、限流、路由、fallback、审计和响应链。

## 前置知识

先读 [4.2 网关与代理项目](../04_real_projects/4.2-gateway-and-proxy.md) 和 [3.5 并发模式](../03_architecture_patterns/3.5-concurrency-patterns.md)。

## 正文

### 问题域

AI Gateway 位于调用方与多个 LLM provider 之间，统一协议和治理，不只是反向代理：

- 路由：tenant/model/provider 能力、健康、成本与延迟共同生成候选。
- fallback：仅对可重试错误和可安全重放的请求换候选，并受总 attempt/deadline 约束。
- 限流：per-tenant、per-model、token budget 与 provider 并发是不同维度。
- 审计：记录 request ID、tenant、model、provider、token、成本和错误类别；敏感 prompt 需脱敏/按政策保存。
- 流式：SSE headers/首个 chunk 写出后通常不能再透明切 provider；还要处理下游断开和上游取消。

### Capstone 包地图

```text
internal/gateway/httpapi/    HTTP decode, status mapping, /healthz
internal/gateway/core/       request model, error classes, orchestration, endpoint
internal/gateway/policy/     tenant authorization and token admission
internal/gateway/router/     deterministic RoutePlan
internal/gateway/provider/   client, registry, queue, bound, breaker, fakes
internal/gateway/fallback/   execute attempts and stop by error class/budget
internal/gateway/audit/      request/cost audit sink
internal/app/                composition and versioned config
```

计划中所谓“provider 客户端管理”分布在 provider registry/decorator；fallback 独立为 executor；策略分 policy。每个包沿不同变化原因切分。

### 请求全链路

`POST /v1/chat/completions`（具体路由见 httpapi）进入 Handler 后解码为 `core.ChatRequest`，调用 `core.Service.Chat`：

```text
Policy.Authorize
 -> Limiter.Admit(tenant, estimatedTokens)
 -> Router.Plan(request, tenantPolicy)
 -> Executor.Execute(request, routePlan)
    -> Registry.Client(route)
    -> Client.Chat(request.WithRoute(route))
    -> telemetry + audit for every attempt
    -> success OR CanFallback(error) OR stop
 -> httpapi maps final error class to status
```

四个接口都由 core 定义，具体 policy/router/fallback 依赖 core。`app.BuildDemo` 是组合根：primary 用超时 fake + breaker，backup 成功，策略允许 fallback，retry budget 为 3。测试证明 fallback 后响应、telemetry 和 audit 同时存在。

### 关键决策

**先规划再执行**：Planner 过滤未授权/不健康 provider、去重并按名称排序兜底，输出确定 RoutePlan；Executor 不再决定策略，只负责按序尝试。优点是易测、可审计，代价是健康可能在执行前变化。

**错误类别驱动 fallback**：timeout/unavailable 等可恢复类别继续，无效请求/权限类立即停。总预算必须覆盖嵌套 retry，避免候选数 × client retry 形成流量放大。

**装饰 provider client**：BoundedClient、Breaker/TimedBreaker 将并发与故障保护包在统一 Client 外。顺序影响行为：breaker 在 bound 外还是内，会决定“本地满载”是否计入下游失败。

**审计与遥测旁路**：本地实现忽略 sink 错误，保证观测故障不阻断主请求；生产需暴露 drop/failure 指标并决定审计是否属于合规强制路径。

### 当前学习实现的边界

已有：租户策略、token admission、确定路由、错误分类、fallback budget、registry、bounded client、breaker、attempt telemetry/audit、配置验证/版本/回滚。

待生产化：真实 provider 与凭据轮换、SSE proxy、分布式 quota、跨实例健康、持久审计、价格表版本、请求体/响应大小限制、TLS/auth、端到端 timeout、指标和负载测试。

### 前端人容易踩的坑

- 将 model 名直接等同 provider 型号，忽略租户映射和版本。
- 在 HTTP handler 里写完整 fallback 循环，无法复用/测试。
- 流开始后仍切 provider，造成拼接出的无效响应。
- 每个 provider 各自返回不同错误，路由层无法稳定判断。
- token 限流只在请求后按实际值结算，入口没有 admission 保护。

## 对比前端

可把 AI Gateway 想成后端的 BFF + 多 SDK adapter + resilience layer，但它必须处理真正并行、跨实例额度、流式半响应和合规审计。前端 fetch wrapper 的 retry/fallback 心智模型只有在请求可重放且尚未输出时成立。

## 检验标准

1. 路由规划和 fallback 执行为何分开？
2. 哪些错误不应 fallback？
3. Client decorator 的顺序会改变什么？
4. SSE 首包之后为什么通常不能透明切换？
5. capstone 距生产网关还缺哪三类能力？
