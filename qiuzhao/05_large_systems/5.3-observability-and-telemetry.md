# 5.3 可观测性与遥测

> 能把 trace、metric、log 关联到同一请求，并设计不会反向拖垮业务的异步遥测管道。

## 前置知识

理解 context、pipeline 与有界队列；建议先读 [3.2 中间件与管道](../03_architecture_patterns/3.2-middleware-and-pipeline.md)。

## 正文

### 三支柱回答不同问题

- trace：一次请求跨服务/阶段经过哪里，延迟和错误落在哪个 span。
- metric：系统整体随时间如何变化，适合 SLO、趋势和告警。
- log：某个离散事件的结构化细节，用 trace/request ID 关联。

不要把同一 JSON 同时叫三种信号。高基数 request ID 适合 trace/log，不适合 metric label；tenant/model/provider 也需评估基数和隐私。

### OpenTelemetry Go 接入形状

在入口提取远端 trace context 并创建 server span；业务函数继续传 `r.Context()`；provider client 注入 trace headers 并创建 client span。context 是传播载体，不应另造全局 trace ID。

```go
ctx, span := tracer.Start(r.Context(), "gateway.chat")
defer span.End()
resp, err := service.Chat(ctx, req)
if err != nil { span.RecordError(err) }
```

生产通常使用 OTel SDK batch span processor 和 OTLP exporter，把数据交给 Collector。业务代码依赖 OTel API/抽象，SDK/exporter 在 main 中组装，并在 shutdown 时 flush。

### 自建学习管道

Capstone 的 `telemetry.Event` 记录 gateway attempt 的 request/tenant/model/provider/error class/fallback index。`Sink` 是最小 exporter seam，MemoryExporter 用于断言；AsyncExporter 是学习版：

```text
Record(ctx, event)
 -> bounded channel
 -> background run
 -> next Sink
queue full -> increment dropped, do not block request
```

这个策略适合可丢的诊断事件。生产实现还需：安全关闭 channel/worker、flush acknowledgement（不能依赖 `len(queue)` 忙等）、批量、retry/backoff、export timeout、drop/retry/failure 指标和 exporter 自身健康。审计事件若有合规要求，不能沿用任意丢弃策略。

### 采样

Head-based 在请求开始时决定，成本低，但可能丢掉后来才知道的罕见错误。Tail-based 在 Collector 聚合完整 trace 后决定，可保留慢/错误 trace，但需要缓存、更多内存与一致路由。常见组合：SDK head sample 限制总量，Collector tail policy 优先错误/高延迟/关键 tenant。

### slog 结构化日志

```go
logger.InfoContext(ctx, "provider attempt",
	"request_id", req.RequestID,
	"tenant_id", req.TenantID,
	"provider", route.Provider,
	"fallback_index", index,
)
```

使用稳定字段名和合适 level；错误在边界记录一次，避免每层重复。prompt、response、Authorization、API key 和工具输出默认视为敏感，不直接记录。logger 可用 `With` 绑定 component/version 等低变化属性。

### 应观测的网关/Agent 指标

- 请求率、错误率、p50/p95/p99 latency，按 model/provider/error class 控制维度。
- provider in-flight、queue depth/reject、breaker state/transition、fallback 次数。
- token/cost，按租户聚合但避免无限 label。
- agent run duration、step/tool count、interrupt/failure、event append conflict。
- telemetry queue depth、dropped、export latency/failure（监控监控系统本身）。

### 前端人容易踩的坑

- 把 console log 全量搬到服务端，不设字段、级别和保留期。
- 每个用户/request ID 都做 metric label，引爆时序数。
- span 创建后不传 context，下游形成断裂 trace。
- exporter 同步发送，遥测后端抖动直接增加业务延迟。
- exporter 无界异步，抖动转化为 OOM。

## 对比前端

前端也有 Performance API、RUM trace 和 analytics batch；后端需要把同一 context 跨 goroutine、HTTP/RPC 和消息传播，并控制高吞吐下的基数与背压。浏览器 analytics 丢几条常可接受，合规审计或计费记录则可能必须走可靠 outbox。
