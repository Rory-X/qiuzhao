# 4.2 网关与代理项目

> 能从 Bifrost、Tyk 和 Caddy 提取路由、策略链与模块生命周期，而不是复制其目录。

## 前置知识

先读 [4.1 如何读 Go 项目](4.1-how-to-read-go-projects.md) 与 [3.2 中间件与管道](../03_architecture_patterns/3.2-middleware-and-pipeline.md)。

## 正文

### maximhq/bifrost：多 Provider AI 网关

阅读地图（目录会随版本演进，应以当前仓库为准）：

```text
cmd/                 executable/control entry
core/                request, provider and routing contracts
transports/          HTTP/provider protocol boundaries
framework/           orchestration, plugins and runtime services
```

先找 provider interface、provider registry/配置和 chat/completion handler，再追一条 OpenAI-compatible 请求：HTTP 解码 → tenant/model 信息 → provider 选择 → 队列/并发保护 → provider client → 统一响应或流式转发。重点验证 fallback 是在路由计划中预先生成，还是失败后再选择；错误类别是否区分可重试、限流和无效请求。

设计亮点是将各厂商协议归一到稳定核心模型，并把 provider 健康、并发队列和 fallback 当一等能力。可提取：`ProviderClient` 小接口、registry、候选 RoutePlan、有界并发、按错误类别 fallback。不要复制其所有 provider/plugin 抽象到只有两个厂商的项目。

### TykTechnologies/tyk：成熟 API Gateway

关键地图：

```text
gateway/             server, API loading, reverse proxy path
gateway/mw_*         authentication, quota, transform and policy stages
internal/            internal services/helpers
apidef/              API and policy configuration contracts
```

一条典型请求从 gateway server/mux 进入，匹配 API definition，经过认证、访问策略、quota/rate limit、请求变换等 middleware，进入 reverse proxy，上游响应再经过响应阶段与分析/日志旁路。具体顺序由 API 类型和配置决定，因此阅读时应从 middleware chain 的组装点验证，而不是按文件名猜。

设计亮点是策略驱动的可组合链、短路响应、分布式限流和异步 analytics。可提取：阶段式策略、统一 session/tenant 上下文、控制面配置与数据面执行分离、best-effort telemetry。代价是全局配置与长期兼容形成的大型对象，不适合作为新项目起点。

### caddyserver/caddy：模块化 Server 平台

关键地图：

```text
cmd/caddy/           CLI and tiny entry
caddy.go             config load/run lifecycle
modules.go           module registry, IDs and loading
admin.go             dynamic configuration API
modules/caddyhttp/   HTTP app, routes and handler chain
```

数据面请求由 `caddyhttp` route 匹配并构建 handler chain；控制面配置则经 admin API 校验、适配、加载新 config，provision 模块并清理旧 config。两条链不要混读。

核心接口/约定围绕 `Module`、ModuleID/Info、Provisioner、Validator、Cleaner 和配置解码。亮点是编译期注册能力 + 运行期声明式组装、明确 lifecycle 和原子配置替换。可提取：typed registry、先全量 validate 再 swap、反向 cleanup；不要在不需要第三方扩展时先造插件平台。

### 横向比较

| 项目 | 稳定核心 | 主要组合轴 | 失败关注 |
|---|---|---|---|
| Bifrost | 统一 AI 请求/provider | provider、route、fallback | 超时、限流、厂商失败 |
| Tyk | API definition + middleware | policy chain | 拒绝、配额、上游错误 |
| Caddy | module + config lifecycle | module graph/route | 配置无效、加载/清理失败 |

三者共同模式是“稳定请求/配置契约 + 可组合执行单元 + 明确边界”。不同点在于 AI 路由关注候选与错误分类，通用网关关注策略链，server platform 关注模块生命周期。

### 前端人容易踩的坑

- 把 fallback 当 `catch { call backup }`，忽略请求是否可重放、流是否已开始。
- 按中间件文件名猜执行顺序。
- 混淆控制面配置变更与数据面请求路径。
- 看到 plugin registry 就为内部两种实现引入动态插件系统。

## 对比前端

Tyk middleware 与 Express/Koa 链形状相似，但还要处理跨实例配额和反向代理流。Caddy module registry 类似前端插件注册表，却包含 provision/validate/cleanup 和配置原子性。Bifrost provider adapter 类似多支付/多地图 SDK 适配，但流式响应一旦写出便难以安全 fallback。
