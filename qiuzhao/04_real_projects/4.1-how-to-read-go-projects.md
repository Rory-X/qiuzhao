# 4.1 如何读 Go 项目

> 能在陌生大型仓库中用一条请求链建立可靠地图，而不是从最大文件开始漫游。

## 前置知识

完成 02 和 03 章；本章示例命令需在目标 Go 仓库根目录运行。

## 正文

### 五步法

1. **从 `cmd/` 找入口**：用 `rg 'func main\('` 找二进制，记录 main 读取什么配置、创建哪些组件、怎样启动/退出。
2. **扫顶层职责**：`find internal pkg -maxdepth 2 -type d`，先根据目录名提出假设，不急着逐文件读。
3. **找核心接口**：`rg -n 'type .* interface' --glob '*.go'`，重点看调用方、构造函数和实现，而非接口数量。
4. **追一条完整链路**：选择一个可观察入口（HTTP route/message/CLI），一路追到业务决策、I/O 和响应。
5. **用测试校准理解**：测试名、fake 和失败断言通常比注释更直接地表达设计意图。

每一步都写一张小卡片：事实、假设、证据路径和未解问题。读完一次链路后再扩展第二条，不要先建立“全仓库百科”。

### 四个观察轴

**依赖方向**：谁 import 谁？核心是否依赖具体框架/driver？`go list -deps` 与编辑器 references 能验证。

**错误路径**：错误在哪里分类、包装、记录、重试和转成协议响应？同时找 `errors.Is/As`、`%w` 和 sentinel。

**并发边界**：哪些函数启动 goroutine，谁拥有 channel/lock，root context 从哪里来，队列满和 shutdown 时发生什么？

**配置注入**：env/file/flag 怎样变成 typed config，何时 validate，运行中能否 reload，旧组件怎样 cleanup？

### 工具清单

```bash
go doc ./internal/foo
go doc ./internal/foo.Type.Method
go list -deps ./cmd/server
go list -json ./internal/foo
go test ./internal/foo -run TestSpecificBehavior -v
go test -race ./internal/foo
rg -n 'NewServer|RegisterRoutes|ServeHTTP|Run\(' --glob '*.go'
```

gopls 的 references、implementations、call hierarchy 比文本搜索更懂语义；`guru` 在旧仓库/特定分析中仍有价值。动态理解优先跑单个测试并加断点，不要先启动所有外部依赖。

### 调用链记录模板

```text
入口: POST /v1/chat
边界: decode -> auth -> quota
核心: plan route -> execute fallback
I/O: provider.Client.Chat
返回: classify error -> JSON/SSE
旁路: audit + metrics (sync or best effort?)
取消: request context reaches provider?
```

区分静态可能路径和测试已经证明的路径。看到接口不等于存在多个实现；看到 goroutine 不等于并发安全。

### 前端人容易踩的坑

- 只读 README/框架配置，以为等同真实运行路径。
- 从 `utils` 或最大 package 开始，失去业务上下文。
- 看到熟悉的 controller/service 名就套用 NestJS 解释。
- 只追成功路径，不追 timeout、queue full、shutdown。
- 用 `go test ./...` 代替理解具体行为；全绿只能说明当前断言通过。

## 对比前端

读 Node 项目常从 `package.json` script、framework module 和 route 开始；Go 的对应起点是 `go.mod`、`cmd/*/main.go`、构造函数与 `http.Handler`/transport 注册。Go 没有 decorator 元数据替你画对象图，显式 `NewX` 链反而更容易追踪。

## 检验标准

1. 为什么先追一条链比先读全部目录有效？
2. 如何验证接口的真实实现与调用方？
3. 阅读并发代码时必须记录哪三个生命周期问题？
4. 测试能校准哪些静态阅读产生的假设？
