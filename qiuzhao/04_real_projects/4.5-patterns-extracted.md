# 4.5 可复用模式提炼

> 能把大型项目中的设计压缩成十个可独立采用的 Go 模式，并知道各自的适用边界。

## 前置知识

读完 04 章前四篇；以下代码是学习版最小形状，不是上游代码复制。

## 正文

### 1. 接口由使用方定义

一句话：调用者只描述自己需要的行为。来源：go-kit、Memos、capstone。

```go
type UserFinder interface {
	Find(ctx context.Context, id string) (User, error)
}
type Handler struct{ users UserFinder }
```

适合隔离 I/O 和测试决策；若只是同包内部调用且没有 seam，不必建接口。变体是单方法函数类型。

### 2. 构造函数注入 + Option

一句话：必需依赖用参数，可选策略用 typed option。来源：Go 生态普遍实践、Caddy 组件组装。

```go
type Client struct { http *http.Client; retries int }
type Option func(*Client)
func WithRetries(n int) Option { return func(c *Client) { c.retries = n } }
func NewClient(h *http.Client, opts ...Option) *Client {
	c := &Client{http: h, retries: 2}
	for _, opt := range opts { opt(c) }
	return c
}
```

不要把必需依赖藏进 Option，也不要允许 Option 组合出无效状态；构造后集中 validate。

### 3. Middleware 装饰器

一句话：通过函数包装在稳定调用边界添加横切行为。来源：go-kit、Tyk、Hertz。

```go
type Endpoint func(context.Context, Request) (Response, error)
func Measure(next Endpoint) Endpoint {
	return func(ctx context.Context, req Request) (Response, error) {
		start := time.Now()
		resp, err := next(ctx, req)
		record(time.Since(start), err)
		return resp, err
	}
}
```

适合日志、指标、认证、限流；核心业务状态转换留在 use case。变体是 `func(http.Handler) http.Handler`。

### 4. 有界队列 + Worker Pool

一句话：同时限制等待量和并行量。来源：Bifrost、NATS、OTel Collector。

```go
type Job func()
type Pool struct{ jobs chan Job }

func NewPool(capacity, workers int) *Pool {
	p := &Pool{jobs: make(chan Job, capacity)}
	for i := 0; i < workers; i++ { go p.work() }
	return p
}
func (p *Pool) work() {
	for job := range p.jobs { job() }
}
func (p *Pool) TrySubmit(j Job) bool {
	select { case p.jobs <- j: return true; default: return false }
}
func (p *Pool) Close() { close(p.jobs) }
```

只有停止所有提交后，队列 owner 才能调用 `Close`。真实实现还需 context、结果/错误、panic 边界和带等待的 shutdown。变体是阻塞、超时或优先级队列。

### 5. Circuit Breaker

一句话：下游持续失败时快速拒绝，并在冷却后试探恢复。来源：网关/provider 系统。

```go
type State int
const ( Closed State = iota; Open; HalfOpen )
type Breaker struct { mu sync.Mutex; state State; failures int; openedAt time.Time }

func (b *Breaker) Allow(now time.Time) bool {
	b.mu.Lock(); defer b.mu.Unlock()
	if b.state == Open && now.Sub(b.openedAt) >= time.Second {
		b.state = HalfOpen
	}
	return b.state != Open
}
```

还需在调用成功/失败后原子迁移状态。仅统计可恢复下游错误，不把用户 400 算入熔断；变体是滑动窗口、按 endpoint 分桶。

### 6. Provider Registry + 健康检查

一句话：通过名称发现运行实例，把配置与调用解耦。来源：Bifrost、Caddy。

```go
type Provider interface { Chat(context.Context, Request) (Response, error) }
type Runtime struct { Client Provider; Healthy bool }
type Registry struct { mu sync.RWMutex; items map[string]Runtime }
func (r *Registry) Get(name string) (Runtime, bool) {
	r.mu.RLock(); defer r.mu.RUnlock()
	v, ok := r.items[name]; return v, ok
}
```

健康是带时间和原因的状态，不应只是永久 bool。变体有被动失败计分、主动 probe 和 immutable snapshot 原子替换。

### 7. Event Store + Replay

一句话：保存不可变事实，由 reducer 重建状态。来源：Temporal、agent runtime。

```go
type Store interface {
	Append(context.Context, string, int, ...Event) error
	Load(context.Context, string) ([]Event, error)
}
func Replay(events []Event) State {
	var s State
	for _, event := range events { s = Apply(s, event) }
	return s
}
```

适合审计、恢复和时间线是核心价值的领域；代价是版本、快照、幂等和乐观并发。变体是状态快照 + 后续事件。

### 8. Pipeline Stage

一句话：每个组件只做一种转换，由配置组合数据流。来源：OTel Collector。

```go
type Processor[T any] interface {
	Process(context.Context, T) (T, error)
}
func Run[T any](ctx context.Context, v T, ps ...Processor[T]) (T, error) {
	var err error
	for _, p := range ps {
		v, err = p.Process(ctx, v)
		if err != nil { return v, err }
	}
	return v, nil
}
```

同步组合最简单；需要隔离吞吐时才增加 queue/batch/retry，并明确顺序与部分失败。

### 9. Graceful Shutdown 模板

一句话：停止入口、取消后台、等待在途，且整个过程有上限。来源：Memos、Caddy、基础设施服务。

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
go func() { _ = server.ListenAndServe() }()
<-ctx.Done()
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := server.Shutdown(shutdownCtx); err != nil { log.Printf("shutdown: %v", err) }
```

多组件应记录启动顺序并反向关闭。变体是 drain queue、停止 leader lease、flush telemetry。

### 10. 配置热加载

一句话：先构建并验证完整新快照，再原子替换，旧快照按生命周期清理。来源：Caddy。

```go
type Store struct { current atomic.Pointer[Config] }
func (s *Store) Swap(next *Config) error {
	if err := next.Validate(); err != nil { return err }
	if err := next.Provision(); err != nil { return err }
	old := s.current.Swap(next)
	if old != nil { return old.Cleanup() }
	return nil
}
```

真实系统还需版本、审计、回滚、并发 reader 生命周期和清理失败策略。不要逐字段原地修改可变全局配置。

### 组合边界

模式不是套餐。一个小 API 可能只需要小接口、构造注入、HTTP middleware 和 shutdown；AI 网关才逐步加入 registry、bounded pool、breaker 和 hot reload；agent history 是核心价值时再用 event store。每引入一个模式，都写清它消除的具体失败模式与新增运维成本。

### 前端人容易踩的坑

- 收集 pattern 名称，却没定义队列满、清理失败、事件冲突等行为。
- 把 Option 变成无类型配置袋。
- breaker 与 retry 叠加造成流量放大。
- 热更新原地 mutate map，引发 race 和半更新状态。
- 所有事件都永久保存，却没有版本与保留策略。

## 对比前端

装饰器/高阶函数、Redux reducer、插件 registry 在前端都有相似形状；Go 版本还必须显式处理 context、并发所有权、资源 cleanup 和进程退出。类型相似不代表可靠性语义相同。
