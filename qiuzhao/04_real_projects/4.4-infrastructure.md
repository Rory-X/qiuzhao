# 4.4 基础设施项目

> 能从 NATS、Temporal 与 OpenTelemetry Collector 识别消息、持久执行和遥测管道的关键边界。

## 前置知识

先读 [3.4 事件驱动与 CQRS](../03_architecture_patterns/3.4-event-driven-and-cqrs.md) 和 [3.5 并发模式](../03_architecture_patterns/3.5-concurrency-patterns.md)。

## 正文

### nats-io/nats-server

阅读地图从 `main`/server options 开始，再看 `server/` 中 client connection、subscription routing、account、JetStream 与 clustering。典型 core NATS 链路是连接解析协议 → 校验 account/permission → subscription trie 匹配 → 将消息写入目标 client outbound；JetStream 还要经过 stream 持久化、consumer state、ack/redelivery。

核心类型围绕 Server、client、subscription/sublist、Account 以及 JetStream stream/consumer。设计亮点是低延迟 pub/sub 路径、连接级 read/write loop、账户隔离和对 slow consumer 的明确策略。可提取：每连接单 owner、批量写、慢消费者断开/丢弃/限额、控制面与热数据路径分离。

### temporalio/temporal

阅读地图先看 `service/frontend`、`service/history`、`service/matching`、`service/worker` 和 persistence/common。请求由 frontend 接受；workflow command 进入 history shard，事件追加到 history；matching 管理 task queue，worker poll 并返回 command；history 根据事件和 command 推进状态。

稳定核心是不可变 workflow history、deterministic replay 与 task token/version 协议。亮点是把“执行”变成可恢复状态机；代价是确定性约束、事件历史增长、版本演进和复杂分布式运维。可提取：append-only history、lease/shard ownership、task queue、幂等 command；不要用普通 goroutine 假装 durable workflow。

### opentelemetry-collector

阅读地图围绕 `receiver/`、`processor/`、`exporter/`、`connector/`、`service/` 与 component contracts。配置声明 pipelines；service/factory 创建组件并按生命周期启动。数据从 receiver 进入，经过零个或多个 processor，再由 exporter 发往后端；queue/batch/retry 常位于 helper 或 exporter 周边。

亮点是稳定的 component/factory/config/lifecycle 契约，以及 traces/metrics/logs 共享管道形状。可提取：typed stage、批处理、bounded sending queue、retry/backoff、self-telemetry。处理遥测本身也必须可观测，并对 overload 做 drop/block 决策。

### 横向比较

| 项目 | 必须守住的事实 | 核心压力 | 失败策略 |
|---|---|---|---|
| NATS | subscription/stream delivery state | 连接与消息吞吐 | slow consumer、redelivery |
| Temporal | workflow event history | shard/task 调度 | replay、retry、ownership |
| OTel Collector | telemetry batch/pipeline | 批量与出口背压 | queue、retry、drop |

三者都依赖明确所有权、有界队列和生命周期，但 durability 不同：core pub/sub 可瞬时，JetStream/history 是持久事实，telemetry 常允许按策略降级。

### 前端人容易踩的坑

- 把 pub/sub 当队列，不理解订阅、ack、持久化和 redelivery 差异。
- 认为 async/await 重试就等于 Temporal 的崩溃恢复。
- 遥测 exporter 无界排队，故障时反而拖垮业务。
- 忽略分区/shard 内顺序与跨分区无序。
- 把基础设施内部实现全部带进业务层，而不是提取边界模式。

## 对比前端

浏览器 EventTarget/Node EventEmitter 是进程内瞬时通知；NATS/JetStream 加入网络、权限和投递语义。前端状态恢复常从服务器重新取快照；Temporal 从完整历史确定性重放。前端 analytics SDK 也会 batch/drop，但 Collector 把这套机制做成可配置的多信号基础设施。
