# 4.3 微服务框架与产品服务

> 能比较 go-kit、Kratos、Hertz 与 Memos 的请求链和抽象成本，按问题选择模式。

## 前置知识

先读 [3.1 Clean Architecture](../03_architecture_patterns/3.1-clean-architecture.md) 和 [4.1 如何读 Go 项目](4.1-how-to-read-go-projects.md)。

## 正文

### go-kit/kit：service → endpoint → transport

```text
service method
 -> endpoint(request DTO -> service -> response DTO)
 -> endpoint middleware
 -> HTTP/gRPC transport decode/encode
 -> transport middleware
```

核心形状是 `type Endpoint func(context.Context, any) (any, error)`，transport 负责协议，endpoint 提供可装饰边界，service 只表达业务。亮点是 transport-independent middleware 和显式分层；代价是类型转换/样板。适合多 transport、横切能力多的服务，不必用于只有几个 handler 的 CRUD。

### go-kratos/kratos：proto-first 服务骨架

关键地图通常是 `cmd/`、`api/`（proto/generated）、`internal/biz`、`internal/data`、`internal/service`、`internal/server`。请求从生成的 HTTP/gRPC binding 进入 service，service 调 biz/usecase，biz 通过 repo interface 访问 data adapter。

亮点是同一 proto 契约生成多 transport、统一 middleware、配置、日志、注册发现。适合组织已有 protobuf/API 治理和微服务基础设施；小服务引入后会承担生成链、分层与框架升级成本。

### cloudwego/hertz：高性能 HTTP

关键地图围绕 `pkg/app` request context、`pkg/route` 路由、`pkg/network` 网络栈、protocol 与 binding/render。请求由 event-loop/network 层解析，路由树匹配 handler chain，`RequestContext` 经过池化/复用，最后编码响应。

亮点是高性能网络与路由、对象池和可插拔协议能力。池化意味着不能在请求结束后保存 context/底层 buffer 引用。只有 profile 证明标准库/常规框架是瓶颈时，性能复杂度才值得。

### usememos/memos：小而完整的产品服务

关键地图是 `cmd/memos/main.go`、`server/server.go`、store 与 API service。main 读取配置并处理 signal；server 同时组合 API、静态前端、health、SSE/广播与后台 runner。一条 memo 写入链可能包含鉴权、主存储、关系/附件、webhook、通知和广播。

亮点是单 binary 中清楚的产品生命周期，以及把主写入与 best-effort 副作用区分。它不是通用 framework，反而展示“按产品问题长出结构”。可提取后台 runner、SSE 生命周期、存储抽象和 graceful shutdown。

### 横向比较

| 项目 | 优先问题 | 核心抽象 | 适用条件 |
|---|---|---|---|
| go-kit | transport 与横切解耦 | Endpoint | 多 transport/中间件 |
| Kratos | proto-first 微服务治理 | generated service + biz/repo | 组织级基础设施 |
| Hertz | HTTP 吞吐与延迟 | RequestContext/route engine | 已证实的性能压力 |
| Memos | 完整产品交付 | Server/store/runners | 小中型产品服务 |

### 前端人容易踩的坑

- 看到框架分层就认为目录越多越专业。
- 在 go-kit endpoint 中重复 service 业务逻辑。
- 修改生成代码，而不是 proto/生成配置。
- 保存池化 request context 到 goroutine，形成 use-after-reuse 风险。
- 把 best-effort 通知失败升级为主写入失败，或反过来吞掉关键事务错误。

## 对比前端

Kratos 接近 proto-first Nest/Connect 生态；go-kit 更像把 controller 函数显式拆成 transport adapter 与可装饰 use-case endpoint；Hertz 类似为高吞吐定制的 HTTP runtime，必须理解 buffer/context 所有权；Memos 则接近不依赖重框架的全栈产品后端。
