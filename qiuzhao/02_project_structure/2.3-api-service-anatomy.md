# 2.3 API 服务解剖

## 正文

### 启动与依赖组装

[`cmd/api/main.go`](api_service/cmd/api/main.go) 依次读取 `ADDR`、创建 `MemoryRepository`、把 `time.Now` 注入 `Service`、创建 Handler，最后启动 `http.ListenAndServe`。

```text
main
 └─ MemoryRepository
    └─ Service(repo, clock)
       └─ Handler(service)
          └─ http.ListenAndServe
```

这就是手写依赖注入：构造函数明确展示对象图，不需要容器。注入 clock 让时间相关逻辑可确定测试。当前 main 是教学最小版；生产版还应使用带 timeout 的 `http.Server`、信号监听和优雅关停。

### 信号处理：当前缺口与生产形状

当前 [`main.go`](api_service/cmd/api/main.go) 直接调用 `http.ListenAndServe`，没有捕获 SIGTERM；容器滚动更新时只能被动结束。生产入口应让 signal 取消 root context，先停止接收新请求，再在独立 deadline 内等待在途 handler：

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

server := &http.Server{Addr: addr, Handler: handler, ReadHeaderTimeout: 5 * time.Second}
go func() {
	if err := server.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
		log.Printf("serve: %v", err)
		stop()
	}
}()

<-ctx.Done()
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := server.Shutdown(shutdownCtx); err != nil {
	log.Printf("shutdown: %v", err)
}
```

完整程序需导入 `context`、`errors`、`os/signal`、`syscall` 等包。清理 context 不能复用已经取消的 root context；后台 worker、数据库与 exporter 也要纳入同一个生命周期顺序。

### HTTP 边界

[`internal/httpapi/handler.go`](api_service/internal/httpapi/handler.go) 实现 `http.Handler` 的 `ServeHTTP`，根据 path 分发 `/healthz`、`/resources`、`/resources/{id}/complete` 和 `/progress`。每个 handler 完成四件事：

1. 验证 method/path 并解码请求。
2. 调用 service，传递 `r.Context()`。
3. 把领域错误集中映射为状态码。
4. 编码 JSON 响应。

`json.Decoder.DisallowUnknownFields()` 可尽早发现拼错字段。边界返回稳定的公开错误，不把 repository 细节泄露给客户端。

### 业务与存储

[`service.go`](api_service/internal/resource/service.go) 保存业务规则：标题 trim 后不能为空、创建时间转 UTC、完成资源前必须存在、进度由资源状态计算。它不知道 HTTP 和 JSON。

[`repository.go`](api_service/internal/resource/repository.go) 在使用方 `resource` 包定义 Repository 接口，内存实现用 mutex 保护 map/order/next 的联合不变量，并在每次操作前尊重 context 取消。将来换数据库时，Service 无需变化。

[`model.go`](api_service/internal/resource/model.go) 定义领域/输出模型和创建输入。这个小项目允许同一 struct 同时承担模型和 DTO；当外部协议与领域演进速度不同、涉及版本或敏感字段时，应在 httpapi 定义 DTO 并在边界转换。

### 一条请求的完整链路

`POST /resources`：

```text
net/http
 -> Handler.ServeHTTP
 -> handleResources -> handleCreate
 -> decode JSON into CreateInput
 -> Service.Create(ctx, input)
 -> validate/normalize/build Resource
 -> Repository.Create(ctx, resource)
 -> assign ID under mutex
 -> writeJSON(201, resource)
```

`PATCH /resources/res-1/complete` 则由 handler 提取 ID，Service 先 `Get`、应用 `Completed=true`，再 `Update`；找不到时 `ErrNotFound` 由 httpapi 映射成 404。

### 不用框架也能有好边界

`net/http` 已提供 handler 接口、context、server、mux 和 `httptest`。框架可提供参数路由、绑定和统一 middleware，但并不会自动产生清晰分层。先理解标准库，才能判断框架减少的是重复代码还是隐藏了重要控制流。

中间件的最小形态：

```go
func Timeout(d time.Duration, next http.Handler) http.Handler {
	return http.TimeoutHandler(next, d, `{"error":"timeout"}`)
}
```

日志、recover、request ID、认证和 timeout 都应包裹 handler；业务授权与领域策略仍属于 service/core。顺序决定语义，例如 recover 通常应覆盖其内层所有组件。

### 前端人容易踩的坑

- handler 直接操作数据库，形成 Express route callback 式大函数。
- 为每层创建完全一样的 DTO，只有字段复制没有边界价值。
- 把 context 换成全局 request 对象。
- 在 repository 中写 HTTP 状态码，倒置依赖。
- 忽略 `http.Server` timeout 和 shutdown，开发环境正常、生产环境泄漏连接。

## 对比前端

| Express/NestJS | 本项目 |
|---|---|
| route/controller | `internal/httpapi.Handler` |
| service/provider | `resource.Service` |
| repository adapter | `resource.Repository` + `MemoryRepository` |
| middleware | `func(http.Handler) http.Handler` |
| DI container | main 中构造函数注入 |

Go 倾向少一层装饰、多一点显式组装；接口放在需要替换依赖的调用方，而不是给每个 class 配一个 interface。
