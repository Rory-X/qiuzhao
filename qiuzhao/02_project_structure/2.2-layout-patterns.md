# 2.2 项目布局模式

> 能根据规模和变更方向选择扁平、标准化或按领域组织的 Go 项目布局。

## 前置知识

先读 [2.1 模块与包](2.1-module-and-packages.md)。

## 正文

### 三种可演进布局

**Flat** 适合一个二进制、职责单一的小工具：

```text
go.mod
main.go
parse.go
parse_test.go
```

不要在只有几百行时预建十层目录。先按行为形成包，再在变化压力出现时拆分。

**cmd + internal** 适合多数服务：

```text
cmd/api/main.go
cmd/worker/main.go
internal/order/
internal/httpapi/
internal/platform/database/
```

`cmd/<name>` 每个目录一个入口，main 负责配置、组装、启动和信号，不承载业务规则。`internal/` 不是一个巨型杂物箱；按职责/领域继续拆包。

**Domain-grouped** 适合业务域较多且各域内部经常一起变化的系统：

```text
internal/order/model.go
internal/order/service.go
internal/order/repository.go
internal/catalog/...
internal/billing/...
internal/platform/...
```

相比顶层 `controller/ service/ repository/` 技术分层，按域组织能让一次业务变更局限在相邻文件；跨域依赖需用明确接口或应用层编排。

### 如何选择

| 情况 | 起点 | 演进信号 |
|---|---|---|
| CLI、实验 | Flat | 出现第二入口或可独立测试的领域 |
| 单服务、小团队 | cmd + internal | 领域之间变化/术语明显分化 |
| 多业务域、中大型团队 | Domain-grouped | 某域需独立部署时再拆 module/service |

项目规模不是只看行数，还看团队所有权、发布节奏、变更耦合与稳定 API 数量。目录是依赖和责任的地图，不是架构等级勋章。

### 不要照搬 project-layout

`golang-standards/project-layout` 是社区目录词典，不是 Go 官方标准。`pkg/`、`configs/`、`scripts/` 并非每个项目都需要。先问“哪个消费者需要这个边界”，再创建目录。尤其不要把内部代码全放 `pkg/`，那会制造公开复用的错误暗示。

### 真实项目的读法

- **memos**：相对紧凑，适合观察小型完整服务如何把 server、store、API 放在有限边界中；学习“够用即可”。
- **go-backend-clean-architecture**：显式 domain/usecase/repository/controller，适合学习依赖反转，但 CRUD 项目照搬会产生重复 DTO 和接口。
- **Tyk**：大型网关包含入口、中间件、策略、存储、插件等长期演化结果；应提取局部模式，不复制目录树。

### 前端人容易踩的坑

- 把 NestJS 的 controller/service/module 三件套复制到每个领域。
- 每个文件一个包，导致命名重复和大量跨包跳转。
- 建一个通用 `utils`/`common`，把无关概念耦合起来。
- 因为未来“可能复用”而建立 `pkg/`；先等真实第二个消费者。
- 在 `main.go` 里实现业务，无法单测也无法复用到 worker。

## 对比前端

前端常按组件类型或框架约定分目录，Go 更看重 package 的内聚 API 与 import 方向。`cmd/` 类似多个应用入口，`internal/` 类似由编译器保护的 monorepo private package；但没有 barrel file，包名应直接表达概念。

## 检验标准

1. 何时 Flat 比“标准布局”更好？
2. `cmd/` 中应该和不应该放什么？
3. 按领域组织如何减少一次业务变更的散布？
4. 为什么 project-layout 不能当脚手架清单？
